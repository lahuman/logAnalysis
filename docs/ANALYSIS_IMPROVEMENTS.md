# 오류 분석·한글 리포트 개선 작업 기록

기준일: 2026-09-09. 브랜치: `codex/important-network`.
작업 시작 기준 커밋: `4289f36`. 패키지 버전은 `0.5.0`을 유지한다.

이번 작업은 깊은 원인 오류를 보존하고, 오류가 발생한 메소드 전체를 분석하며,
담당자가 오류의 긴급도와 대응 방법을 한글 리포트에서 판단하도록 개선했다.
기존 파일·ES·Oracle 입력, Git 조회, 상태 DB와 이벤트별 리포트 구조를 사용하며
새 외부 의존성은 추가하지 않았다.

### 1. 가장 깊은 원인과 발생 위치 보존

일반적인 `Caused by:` 체인은 기존에도 마지막 주 원인을 선택했다. 그러나 입력이나
분석 요청의 크기를 제한할 때 앞부분만 남겨 하단 원인이 사라질 수 있었고,
중첩된 `Suppressed:` 안의 원인이 주 원인으로 잘못 선택되는 경우가 있었다.

- 파일 입력, Java 파서, 분석 요청과 정제 단계의 스택 길이 제한에 공통 보존 로직을 적용했다.
- 길이가 제한을 넘으면 마지막 유효한 주 원인의 `Caused by:`부터 보존한다.
- 원인 구간도 크면 그 앞부분을 보존한다. 해당 구간의 첫 프레임이 예외 발생 위치이며,
  단순히 로그의 마지막 프레임을 선택하는 방식이 아니다.
- `Suppressed:`와 그 내부 원인은 주 원인에서 제외한다.
- 생략은 `[STACK_TRACE_TRUNCATED]`로 표시하며 파서가 확인하면 `stack_trace_truncated` 경고를 남긴다.
- 선택한 원인 예외와 프레임을 fingerprint, Git 소스 조회, LLM 요청에 전달한다.

상위 스택이 생략되면 `... N more`를 완전히 복원하지 못할 수 있다. 이미 수집 단계에서
잘린 로그는 복구하지 않는다. 특히 Oracle의 CLOB 읽기와 문자열 상한은 기존대로
앞부분을 제한하므로, 그 전에 누락된 하단 원인까지 이번 변경이 보존하는 것은 아니다.
입력 형식과 범위는 [로컬 파일 안내](LOCAL_FILES.md)를 참고한다.

### 2. 오류 메소드 전체 분석

`analysis.source_context_lines`는 오류 줄 앞뒤의 최소 범위로 사용한다.
오류 줄을 포함하는 메소드나 생성자를 찾으면 선언부부터 닫는 중괄호까지 범위를 확장한다.
실제 오류 줄 번호는 유지하고 `context_start_line`·`context_end_line`과 소스 내용을 함께 갱신한다.

탐색 시 주석·문자열·문자 리터럴·텍스트 블록의 내용을 제외하고 괄호를 대응시킨다.
다중 행 선언, 애너테이션, 오버로드, 생성자, 람다와 익명 클래스의 중첩 메소드를 검증했다.
오버로드는 메소드 이름만이 아니라 실제 오류 줄의 포함 관계로 선택한다.

전체 Java 문법을 해석하는 컴파일러는 아니다. 초기화 블록, 불완전한 소스 또는 인식하지
못하는 선언에는 기존 오류 줄 주변 범위를 사용한다. 배포 커밋 우선 조회와 로컬 ref 고정,
소스 파일 크기 상한, 파일·라인 근거 검증은 유지한다.

분석 요청과 정제 단계에서 소스를 다시 잘라 보내지 않는다. 요청 원문이 100000자를 넘거나
정제한 소스가 기본 60000자를 넘으면 해당 분석을 실패로 기록한다. 메소드 일부만 보내면서
전체를 분석했다고 표시하지 않는다. 자세한 상한은 [설정 안내](CONFIGURATION.md)에 있다.

### 3. 오류 수준과 대응 판단

| 수준 | 판단 기준 | 기본 권장 대응 |
|---|---|---|
| **높음** | 서비스 중단, 핵심 기능의 지속 실패, 데이터 손상·유실 또는 보안 영향의 근거 | 즉시 영향 확인·담당자 공유·피해 확산 방지·복구 착수 후 원인 수정과 회귀 검증 |
| **중간** | 기능 실패가 있으나 범위가 제한적이거나 미확인 | 당일 업무 시간 내 영향 점검, 임시 대응과 수정 일정 확정; 영향 확대 시 즉시 상향 |
| **낮음** | 격리되고 복구 가능하며 서비스·데이터 영향이 경미하다는 근거 | 모니터링하며 다음 정기 개선에 반영; 반복 증가나 사용자 영향 발생 시 재평가 |

분석 결과의 `error_priority`에 `level`, `rationale`, `impact`, `response_action`,
`escalation_condition`, `provisional`을 저장한다. 새 LLM 응답에는 이 필드를 필수로 요구하며,
누락·잘못된 값은 기존 구조화 응답 수정 절차의 대상이다. OpenAI, NVIDIA NIM과 내부 onprem
경로에 공통 적용하고 정제·캐시·리포트 단계에서도 보존한다.

영향을 판단할 근거가 부족하면 **중간·잠정 판단**으로 표시한다. `NO_SOURCE` 또는 분류가
없는 과거 결과도 같은 안내를 사용한다. 근거 부족 상태를 낮음으로 분류하지 않도록 검증한다.
원본 로그의 ERROR·FATAL, 코드 변경 위험도인 `recommended_fixes.risk`와 오류 수준은 별개다.
처리 시점은 조직의 SLA를 확정하는 값이 아니며 실제 영향과 운영 기준으로 최종 판단한다.

### 4. 한글 출력과 세 줄 요약

- 기본 템플릿과 패키지 내 대체 템플릿의 제목·처리 상태·안내·변경 위험도를 한글화했다.
- 모든 LLM 설명 필드에 한글 출력을 지시한다. 실제 모델의 한국어 품질은 실서버 확인이 필요하다.
- 원문 오류·스택·파일 경로·코드는 검색과 근거 확인을 위해 유지한다.
- 각 리포트 끝에 판단·영향·대응을 각각 한 줄로 요약한다. 개행을 정리하고 긴 문장은 줄인다.
- `run`은 리포트 처리와 자원 정리를 마친 뒤 UTF-8 표준 출력에 전체 결과를 세 줄로 출력한다.
- 기존 JSON 진단 로그는 표준 오류로 출력하며 기존 종료 코드 정책을 유지한다.

```text
처리 완료: 리포트 4건(분석 완료 3건, 소스 미확인 1건), 중복 확인 2건.
오류 수준: 높음 1건 · 중간 2건 · 낮음 1건(소스 미확인은 중간·잠정 판단). 높음 오류부터 즉시 대응하세요.
남은 작업: 재시도 대기 0건 · 실패 0건 · 정리 실패 0건. 결과: reports
```

수준별 건수는 이번 실행에서 생성한 리포트 수이며 캐시로 새로 작성한 리포트도 포함한다.
소스 미확인은 중간·잠정 판단으로 집계한다. 중복 확인 건수에는 이미 등록된 미완료 작업의
재개가 포함될 수 있으므로 모두 건너뛴 건수라는 뜻은 아니다. 중단 시 `처리 중단`을 표시하고,
리포트가 없는 실행도 세 줄로 안내한다. 자원 종료 실패 시 완료 요약을 출력하지 않는다.

기존 사용자 정의 템플릿에는 오류 수준 안내가 없으면 추가하고 마지막 세 줄 요약도 붙인다.
사용자 정의 템플릿 자체의 영문 문구를 자동 번역하지는 않는다.
[한글 합성 리포트](examples/error-priority-report.md)는 새 출력 형식을 보여 주는 수동 작성 예시이며
실제 장애나 실서버 LLM 분석 결과가 아니다.

## 기존 데이터와 적용 방법

패키지 `0.5.0`, 설정의 프롬프트 `java-incident-v2`, 분석기 버전 `1`은 유지한다.
파이프라인의 캐시 분석기 식별값에는 `:full-method-v1:priority-v1:ko-v1`을 붙여
이전 부분 소스·분류 없음·이전 언어 정책의 결과를 새 분석에 재사용하지 않는다.

이미 완료한 이벤트와 기존 리포트는 자동 재분석·일괄 재작성하지 않는다.
저장된 재시도 요청의 소스 범위도 자동 재수집하지 않는다. 운영 데이터나 상태 DB를
삭제하지 않고 기존 중복·복구 정책을 유지한다. [중복 처리 안내](DUPLICATE_ERRORS.md)를 참고한다.

저장소 소스를 사용하는 환경은 현재 브랜치의 소스를 반영하고 기존 설정으로 실행한다.
새 설정 항목이나 의존성 설치는 필요하지 않다. 배포 압축파일은 이번 작업에서 재빌드하지 않았으므로,
폐쇄망 배포본에는 [소스 반영 안내](OFFLINE_DEVELOPMENT.md) 또는 [재빌드 절차](OFFLINE_DEPLOYMENT.md)를 적용해야 한다.

주요 회귀 검증은 긴 원인 체인·중첩 suppressed·Git 실제 임시 저장소 조회,
메소드 경계·소스 용량 초과 거부, 3단계 값·잠정 판단·응답 보정,

```powershell
.venv/Scripts/python.exe -X utf8 -m unittest discover -s tests -q
.venv/Scripts/python.exe -m compileall -q src tests

git diff --check
```

이번 결과는 로컬 코드·모의 HTTP 응답 기반이다. 실제 ES·Oracle·LLM 연결, 실제 모델의
한국어 설명과 오류 수준 판단 품질, RHEL 대상 재빌드·설치·systemd 운영은 검증하지 않았다.
과거 실연동 기록은 [검증 현황](VALIDATION_STATUS.md)에서 시점별로 구분한다.
