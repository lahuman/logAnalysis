# 중복 오류와 리포트 이후 재발 처리

현재 버전은 **동일 이벤트의 재처리를 막고, 같은 유형의 새 이벤트에는 분석 결과를 재사용**한다.
리포트는 이벤트별로 생성한다. 이 동작은 인터넷 LLM과 중요망 onprem에 공통으로 적용된다.

## 1. 동일 이벤트의 재조회

SQLite의 `수집원 이름 + 이벤트 ID`를 기준으로 이미 등록한 이벤트인지 확인한다.
ES의 이벤트 ID는 로그의 `event.id`이며, 없으면 ES의 `인덱스명:_id`를 사용한다.
Oracle은 `error_source.columns.event_id`에 매핑된 컬럼을 사용한다. ID는 고유하며
변경·재사용하지 않아야 한다. ES에서 Oracle로 전환할 때는 수집원 이름을 분리하며
저장소 사이에서 같은 사건인지를 자동으로 판별하지 않는다. [Oracle 안내](ORACLE.md)를 참고한다.

처리 완료한 이벤트를 다시 조회하면 분석·리포트 생성을 건너뛴다. 작업 행을 중복 삽입하지
않으므로 발생 건수도 늘어나지 않는다. 서로 다른 발생 로그에는 서로 다른 ID를 부여해야 한다.
같은 ID의 문서 내용을 바꾸거나 모델 설정을 변경해도 완료 이벤트가 자동 재분석되지는 않는다.

재시도 대기 이벤트는 저장된 재시도 일정으로 처리한다. 중단된 비종료 작업은 복구 대상이므로
단순히 중복이라는 이유로 모두 버리는 것은 아니다. 이 기준은 처리 이력이 보존된 동안 유효하다.

## 2. 같은 유형의 새 이벤트

새 이벤트는 별도 작업으로 기록하고 다음 정보로 fingerprint를 만든다.

| 구성 요소 | 포함하는 내용 |
|---|---|
| 서비스 | 서비스명과 실행 환경 |
| 오류 | 파서가 선택한 예외 종류와 정규화한 메시지 |
| 소스 위치 | 애플리케이션 frame 최대 3개의 클래스·메서드·파일·라인 |

메시지는 정규식에 일치하는 UUID·긴 16진수·5자리 이상 숫자를 공통 표기로 바꾸고
연속 공백을 정리한다. 다른 조건이 같다면 아래 두 메시지는 같은 유형으로 묶일 수 있다.

```text
order 123456 failed → order <number> failed
order 987654 failed → order <number> failed
```

모든 숫자나 가변 문자열을 지우지는 않으며 파일·라인도 판별에 포함된다. 의미를 이해해
원인을 확정하는 방식은 아니다. 같은 fingerprint라도 실제 원인이 반드시 같다는 뜻은 아니다.

## 3. 분석 결과 재사용 조건

다음 캐시 키가 모두 같은 결과가 있으면 LLM을 호출하지 않고 저장한 분석 결과를 사용한다.

```text
fingerprint + 실제 조회한 Git commit + 모델 ID + 프롬프트 버전 + 분석기 식별값
```

onprem 분석기 식별값에는 공급자·API 주소·구조화 출력 모드·thinking 설정이 반영된다.
새 이벤트의 해당 조건이 달라지거나 캐시가 없으면 새로 분석한다. 모든 설정 항목이 캐시 키에
포함되는 것은 아니다. 이미 완료한 이벤트의 자동 재분석과도 구분해야 한다.

동일 캐시 키로 동시에 처리되는 작업은 잠금으로 순서를 제어한다. 먼저 처리한 작업이
분석·저장을 완료하면 뒤의 작업이 캐시를 재사용한다. 실패·재시도·응답 수정 요청까지 포함해
LLM HTTP 요청이 무조건 한 번으로 제한되는 것은 아니다.

## 4. 리포트 작성 이후 같은 오류가 발생하면

아래는 이벤트 ID가 모두 다르고, 소스와 분석 조건이 같으며, 첫 분석이 성공한 예다.

| 시각 | 발생 상황 | 분석 | 리포트 |
|---|---|---|---|
| 10:00 | 최초 이벤트 A | LLM 분석 | A 생성 |
| 10:10 | 같은 유형의 새 이벤트 B | 캐시 재사용 | B 생성 |
| 10:20 | 같은 유형의 새 이벤트 C | 캐시 재사용 | C 생성 |
| 후속 조회 | 이미 완료한 A를 재조회 | 건너뜀 | 추가 생성 없음 |

**기존 A 리포트의 건수나 발생 시각을 갱신하지 않는다.** 새로운 발생 이력은 SQLite에
기록하고, 새 이벤트의 리포트를 생성한다. 따라서 분석 비용은 줄어도 파일 수는 늘어날 수 있다.

리포트의 수치는 다음처럼 읽는다.

- **Occurrences**: 작성 시점에 DB에 보존된 동일 fingerprint·Git commit의 작업 수다.
  병렬 등록·소스 조회 진행과 보존 정리의 영향을 받으며 최종 누적 총계가 아니다.
- **First seen / Last seen**: 현재는 해당 이벤트의 발생 시각을 양쪽에 기록한다.
  같은 오류 그룹 전체의 최초·최종 발생 시각을 집계한 값이 아니다.

LLM 분석에 필요한 소스를 찾지 못한 경우에는 `NO_SOURCE` 리포트를 만들며 LLM을 호출하지 않는다.

## 5. 재시작과 보존 정책

처리 이력과 캐시는 SQLite에 저장되어 프로세스를 재시작해도 유지된다.
중요망 배포본의 기본 경로는 `data/state.db`다.

보존 설정은 `report.retention_days`이며 기본 30일이다. 종료 작업의 갱신 시각과 캐시의
마지막 사용 시각을 기준으로 정리한다. 삭제된 이력·캐시는 이후 재조회 시 중복 판단이나
결과 재사용에 사용할 수 없다. 따라서 Occurrences를 장기간의 영구 통계로 사용하면 안 된다.

## 후속 개선안 — 아직 구현되지 않음

오류 유형별 대표 리포트 하나에 재발 건수·최종 발생 시각을 갱신하고, 소스나 분석 조건이
달라지면 새 분석 버전을 남기는 방식을 검토했다. 현재는 대표 리포트 자동 갱신, 그룹의
최초·최종 발생 시각 집계, 해결·재발 상태 관리가 구현되어 있지 않다.
