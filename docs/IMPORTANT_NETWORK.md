# 중요망 브랜치 작업 정리

기준일: 2026-09-05. 브랜치: `codex/important-network`. 애플리케이션 버전: `0.2.0`.

이 도구는 Java 오류 로그와 소스 코드를 함께 분석해 담당자가 원인 후보, 수정 방법,
검증 절차를 빠르게 파악하도록 돕는다. 중요망 브랜치는 외부 인터넷 없이 내부 LLM을
사용하고, 분석기를 압축 해제 후 설정하여 실행하는 배포 방식을 추가했다.

## main에서 추가한 내용

기준 main 커밋은 `514b03f`, 중요망 기능 구현 커밋은 `cc4b545`이다.

| 영역 | 중요망 브랜치에서 추가한 동작 |
|---|---|
| LLM | `provider="onprem"`으로 명시된 내부 Chat Completions 서버 호출 |
| 연결 | 사설 CA, Bearer 인증, 명시적으로 선택하는 HTTP·무인증 연결 |
| 통신 | 중요망 실행기의 클라우드 provider 거부, 환경 변수 프록시 비사용 |
| 배포 | RHEL 9 x86_64용 Python 3.11.8·의존성 24개·로컬 Git 포함 tar.gz |
| 실행 | `doctor`, `check-config`, `smoke`, `healthcheck`, `run` |
| 검증 | 파일 manifest·SHA-256, 일반 사용자·외부 네트워크 차단·공백 경로 검증 |
| 문서 | 압축 해제, 내부 서버 설정, 인증, 첫 분석, 스케줄링, 버전 교체 안내 |

기존 Java 파싱, ES 수집, Git 소스 조회, 중복 제거, 분석 캐시와 이벤트별 리포트 방식을
유지한다. 리포트 작성 후 재발한 오류도 별도 이벤트로 기록한다.

## 준비부터 운영까지

1. **내부 환경 준비**: Elasticsearch에 Java 오류를 수집하고, 내부 LLM 서버·모델과
   분석 대상 애플리케이션의 완전한 Git 저장소를 준비한다.
2. **배포본 제작**: 인터넷 연결 Linux의 빌더에서 Python·의존성·Git을 묶고 체크섬을 만든다.
3. **중요망 반입**: 압축파일과 `.sha256` 파일을 반입해 검사하고 실행 가능한 디렉터리에 푼다.
4. **실행 환경 점검**: `./log-analyzer doctor`로 네트워크 없이 런타임·무결성·파일 작업을 확인한다.
5. **내부 설정**: `config/config.toml`에 ES·LLM 주소, 모델 ID, 서비스·Git 경로를 설정하고
   인증키는 `config/credentials/`, 사설 CA는 `config/certs/`에 준비한다.
6. **첫 연결 검증**: `check-config` → `smoke` → `healthcheck` 순서로 확인한다.
7. **실제 분석**: `run`으로 오류를 분석하고 `data/reports/`의 Markdown을 검토한다.
8. **주기 운영**: 확인된 명령을 cron 또는 systemd에 등록하고, 상태·리포트·소스를 관리한다.

실제 분석은 다음 순서다.

```text
내부 ES 오류 조회 → 이벤트 중복 확인 → Java 예외·파일·라인 파싱
→ 로컬 Git 소스·변경 이력 조회 → 전송 내용 정제·크기 제한
→ 캐시 조회 또는 내부 LLM 분석 → 응답·소스 근거 검증
→ 이벤트별 Markdown 리포트와 SQLite 처리 상태 저장 → 담당자 검토
```

대상 서버에서 pip·dnf 설치나 컨테이너 실행은 필요하지 않다. 기본값은 동봉된
Python 3.11.8이며, 이미 설치된 정확한 3.11.8 실행 파일을 지정하는 방법도 제공한다.
LLM GPU 서버·모델 가중치·Elasticsearch와 실제 애플리케이션 Git 저장소는 별도 준비 대상이다.

## 중복과 재발 처리

| 상황 | 현재 처리 |
|---|---|
| 처리 완료한 이벤트를 다시 조회 | 건너뛰며 발생 건수를 다시 늘리지 않음 |
| 같은 오류가 새 이벤트 ID로 재발 | 새 발생 이력과 새 리포트 생성; 분석 조건이 같으면 캐시 재사용 |
| 새 이벤트의 소스 commit·모델·분석 식별값 변경 | 해당 조건의 캐시가 없으면 새 분석 |
| 기존 리포트 이후 재발 | 기존 리포트는 유지하고 새 이벤트의 리포트를 추가 |

캐시는 LLM 호출을 줄이지만 리포트 파일을 하나로 합치지는 않는다.
판별 기준과 건수·발생 시각의 의미는 [중복 오류와 재발 처리](DUPLICATE_ERRORS.md)를 참고한다.

## 확인한 결과

| 검증 | 결과 |
|---|---|
| Windows / Python 3.11.8 | 123개 실행, 118 통과·5 제외 |
| Rocky Linux 9 / 동봉 Python 3.11.8·Git | 123개 실행, 119 통과·4 제외 |
| 실제 압축파일 / 일반 사용자 / 외부 통신 차단 | 재배치, HTTP·Bearer 인증, HTTPS 사설 CA, 리포트 생성, Git 조회, 변조 감지 통과 |
| 반입 파일 검사 | 체크섬 확인, 패키지 소스 일치, 실제 인증키 미포함 확인 |

Windows 제외 항목은 ES 통합 3개·POSIX 잠금 2개이며, Linux 제외 항목은 ES 통합 3개·
Windows 전용 1개다. 내부 LLM 검증에는 합성 응답 서버를 사용했으며 실제 모델 품질 검증은 아니다.
자세한 범위와 과거 실제 ES·NIM 검증은 [검증 현황](VALIDATION_STATUS.md)에 기록했다.

## 반입용 산출물

기존에 제작·검증한 압축파일의 기준 코드는 `cc4b545f3d0f28d09a002cb3b8440720c1071e3b`다.
이후 문서 정리는 GitHub 중요망 브랜치에서 확인한다.

| 항목 | 값 |
|---|---|
| 파일 | `log-analyzer-0.2.0-rhel9-x86_64-python3.11.8.tar.gz` |
| 크기 | 약 54 MiB |
| SHA-256 | `0397a2d0cbae63bf2711fc5a25760fdd8a462c372ca6ef8ed4a051f695354afa` |
| 로컬 결과 디렉터리 | 저장소의 `dist/offline/` |
| 함께 보관할 파일 | 같은 이름의 `.sha256`, `verification.json` |

압축파일은 Git 추적 대상이 아니다. GitHub의 소스 ZIP은 런타임을 포함한 반입용 압축파일과
다르다. 새 배포본이 필요하면 [빌드·반입 절차](OFFLINE_DEPLOYMENT.md)를 따른다.

## 다음 작업 후보와 미검증 사항

- **실제 연계**: 내부 LLM 제품·모델·endpoint 선정 후 실제 ES → Git → LLM 전체 배치를 확인한다.
- **최종 서버 확인**: 운영 계정, 내부 DNS·CA, 송신 ACL, 스케줄러, SELinux·FIPS 요구를 확인한다.
- **리포트 개선안 — 미구현**: 오류 유형별 대표 리포트를 유지하고 재발 건수·최종 발생 시각을
  갱신하며, 소스나 분석 조건 변경 시 새 분석 버전을 남기는 방식이다. 현재 이벤트별 리포트
  동작과 구분하며, 그룹 기준·재발 이력 보존 방식을 정해 구현할 후속 항목이다.
